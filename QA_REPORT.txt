[ISSUE-01] SEVERITY: CRITICAL
Category: Workflow Bug
File: frontend/src/components/dashboard/CompanyDashboard.tsx
Title: Admin "Approve & Lock" will always fail with 400 from backend

Detail:
  The CompanyDashboard shows "Approve & Lock" for years with status
  SUBMITTED or UNDER_REVIEW. However the backend finalize() service
  enforces: reviewStatus MUST be "UNDER_REVIEW" to finalize.
  If an admin clicks "Approve & Lock" on a SUBMITTED year (which has
  not yet been moved to UNDER_REVIEW), the backend returns:
    400 Bad Request: "Can only finalize years under review"
  Similarly, "Request Revisions" also requires UNDER_REVIEW status.
  There is no "Start Review" button in the UI to transition
  SUBMITTED -> UNDER_REVIEW first.

Fix: Add a "Start Review" button for SUBMITTED years:
  {fy.reviewStatus === 'SUBMITTED' && !fy.isLocked && (
    <button onClick={() => startReview(fy.id)}>
      Start Review
    </button>
  )}
  And add the handler:
  const startReview = async (yearId: string) => {
    await reviewService.startReview(yearId);
    loadFinancialYears();
  };

[ISSUE-03] SEVERITY: HIGH
Category: Security
File: backend/prisma/seed.ts (line 18)
Title: Default Super Admin password hardcoded in source code

Detail:
  const hashedPassword = await bcrypt.hash('Admin@123456', 12);
  Anyone with repo access knows the default admin password.
  If the seed is run on a production database without changing this,
  the Super Admin account is trivially compromised.

Fix:
  Read from environment variable:
  const password = process.env.SEED_ADMIN_PASSWORD;
  if (!password) throw new Error('Set SEED_ADMIN_PASSWORD env var');
  const hashedPassword = await bcrypt.hash(password, 12);

[ISSUE-04] SEVERITY: HIGH
Category: Logic Bug
File: frontend/src/components/dashboard/AdminDashboard.tsx
Title: Admin dashboard reads from local Zustand store, not the API

Detail:
  AdminDashboard reads: const users = useAppStore(state => state.users)
  The store's users[] array is NEVER populated from the API. It starts
  empty and is only populated by the deprecated local createUser() action.
  Result: The admin dashboard always shows "No students found" even when
  students exist in the database.
  Same issue in SuperAdminDashboard.tsx — it also reads state.users.

Fix: Both dashboards need to fetch users from the API on mount:
  useEffect(() => {
    userService.getUsers().then(res => setUsers(res.data.data));
  }, []);
  Use local state, not the Zustand store's deprecated users array.

[ISSUE-05] SEVERITY: HIGH
Category: Logic Bug
File: frontend/src/components/dashboard/SuperAdminDashboard.tsx
Title: Ban/Unban/Role-change actions only mutate local Zustand store

Detail:
  banUser(), unbanUser(), updateUserRole() all call Zustand store actions
  which only update the local in-memory state. They do NOT call the API.
  So banning a user in the UI has zero effect on the database.
  On page refresh, the user appears active again.

Fix: Replace store actions with API calls:
  const handleBan = async (userId: string) => {
    await userService.updateStatus(userId, 'BANNED', 'Violation');
    // then refresh local user list
  };

[ISSUE-08] SEVERITY: MEDIUM
Category: Security
File: backend/src/modules/company/company.service.ts — softDelete()
Title: No existence check before soft-deleting a company

Detail:
  softDelete() calls hasAccess() then immediately calls prisma.company.update()
  without verifying the company exists and is not already deleted.
  If the company doesn't exist, Prisma throws an unhandled P2025 error
  (record not found) which bypasses the globalErrorHandler and returns
  a raw 500 instead of a clean 404.

Fix: Add before the update:
  const company = await prisma.company.findUnique({ where: { id } });
  if (!company || company.isDeleted) throw ApiError.notFound("Company not found");

[ISSUE-10] SEVERITY: MEDIUM
Category: Logic Bug
File: frontend/src/components/dashboard/ProfilePage.tsx
Title: Email verification status shown incorrectly

Detail:
  The profile page shows "Verified" if user.status === 'ACTIVE' and
  "Not Verified" otherwise. But status and emailVerified are separate
  fields. A user can be ACTIVE but have emailVerified: false (edge case),

  {(currentUser as any).emailVerified ? (
    <span className="text-green-400">Verified</span>
  ) : (
    <span className="text-red-400">Not Verified</span>
  )}
  Note: The User interface in useAppStore.ts does not include emailVerified.
  Add it to the User interface.

[ISSUE-11] SEVERITY: MEDIUM
Category: Configuration
File: backend/prisma/schema.prisma
Title: datasource block missing url field — Prisma CLI commands will fail

Detail:
  datasource db {
    provider = "postgresql"
    // No url field!
  }
  Standard Prisma CLI commands (prisma migrate dev, prisma db push,
  prisma studio) require the url field in the schema. Without it,
  running any migration command will fail with:
    "Error: The datasource url is required"
  The adapter-based approach in prismaClient.ts works at runtime but
  the CLI tooling is broken for all developers.

Fix: Add url to the datasource block:
  datasource db {
    provider = "postgresql"
    url      = env("DATABASE_URL")
  }

Category: UX / Logic
File: frontend/src/components/dashboard/CompanyDashboard.tsx
Title: loadFinancialYears() called without await in action handlers

Detail:

    toast.success('Submitted successfully', { id: toastId });

[ISSUE-14] SEVERITY: LOW
Category: Inconsistency
File: Multiple backend controllers
Title: Inconsistent API response shape across controllers

Detail:
  company/review/financialYear controllers return:
    { message, statusCode, data }
  notification/stats/auth controllers return:
    { success: true, message, statusCode, data }
  The frontend httpClient interceptor returns response.data directly,
  so callers get different shapes depending on which endpoint they hit.
  This makes frontend error handling fragile.

Fix: Create a single shared sendResponse() utility in /shared/ and use
  it in all controllers with a consistent shape:
    { success: true, message, statusCode, data }
