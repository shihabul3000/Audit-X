PROBLEM 1 — CRITICAL: Login never sets a session cookie
================================================================================

WHAT IS HAPPENING:
  When a user logs in via POST /api/v1/auth/login, the response returns
  HTTP 200 with the user data, but NO Set-Cookie header is included.
  This means the browser never receives a session cookie.

  Every subsequent authenticated request (GET /auth/me, GET /companies,
  etc.) requires the Better Auth session cookie. Without it, every
  protected endpoint returns 401 "Authentication required".

  Result: After login, the user is redirected to /dashboard, which
  immediately calls GET /auth/me, gets a 401, calls clearAuth(), and
  redirects back to /auth. The user is stuck in a login loop and
  CANNOT access the dashboard at all.

WHY IT HAPPENS:
  The login flow has two separate auth systems that are not synchronized:

  System 1 — Custom auth (backend/src/modules/auth/auth.service.ts):
    - Validates email/password against the custom `users` table
    - Returns user data on success
    - Does NOT create any session

  System 2 — Better Auth (auth.utils.ts):
    - Manages sessions in the `session` table
    - Issues the session cookie via auth.api.signInEmail()
    - Requires the user to also exist in the `account` table

  The problem: Users created via the custom register endpoint are only
  written to the `users` table. They are NOT written to Better Auth's
  `account` table. So when login calls auth.api.signInEmail(), Better
  Auth says "Credential account not found" and throws an error.

  The current code wraps this in try/catch and silently ignores the
  failure — so login "succeeds" but no cookie is ever set.

  The seeded admin (admin@audit-x.com) also has no account record,
  which is why even the admin cannot log in properly.

WHERE TO FIX:
  File: backend/src/modules/auth/auth.service.ts — register()
  The register function now creates an account record (this was added
  recently), but existing users (including the seeded admin) have no
  account record. You need to:

  Option A (Recommended): During login, if Better Auth signInEmail fails,
  create the account record on-the-fly and retry:

    // In auth.controller.ts login(), replace the try/catch block with:
    try {
      const session = await auth.api.signInEmail({ body: { email, password } });
      // forward cookie...
    } catch {
      // Account record missing — create it and retry once
      const user = await prisma.user.findUnique({ where: { email } });
      if (user) {
        await prisma.account.upsert({
          where: { id: `acc_${user.id}` },
          create: {
            id: `acc_${user.id}`,
            accountId: user.id,
            providerId: "email",
            userId: user.id,
            password: user.password, // already hashed
            createdAt: new Date(),
            updatedAt: new Date(),
          },
          update: {},
        });
        try {
          const session2 = await auth.api.signInEmail({ body: { email, password } });
          // forward cookie...
        } catch { /* still fails, proceed without cookie */ }
      }
    }

  Option B: Migrate all existing users — run a one-time script to create
  account records for all users that don't have one.

  Option C: Replace Better Auth session management entirely with a custom
  JWT/cookie approach (larger refactor).

HOW TO VERIFY THE FIX:
  After fixing, the login response headers should include:
    Set-Cookie: better-auth.session_token=...; Path=/; HttpOnly; SameSite=Lax

PROBLEM 2 — CRITICAL: Frontend port mismatch breaks CORS
================================================================================

WHAT IS HAPPENING:
  The frontend is configured to run on port 3000 (package.json: "vite --port=3000").
  The backend CORS is configured to allow origin http://localhost:3000 (backend/.env).
  This part is correct.

  HOWEVER: When port 3000 is already occupied (e.g., from a previous session),
  Vite automatically picks the next available port (3001, 3002, etc.).
  The new process output shows: "Local: http://localhost:3001/"

  When the frontend runs on port 3001, all API requests are blocked by CORS
  because the backend only allows http://localhost:3000.
  The browser will show: "CORS policy: No 'Access-Control-Allow-Origin' header"

WHERE TO FIX:
  1. Always kill old processes before starting new ones:
     Run: npx kill-port 3000 3001 5000 (or use Task Manager)

  2. Or make CORS more flexible in development:
     File: backend/src/app.ts
     Change:
       origin: config.FRONTEND_URL,
     To:
       origin: (origin, callback) => {
         const allowed = [config.FRONTEND_URL, 'http://localhost:3001'];
         if (!origin || allowed.includes(origin)) callback(null, true);
         else callback(new Error('Not allowed by CORS'));
       },

PROBLEM 6 — HIGH: Opening a financial year shows blank/default data
================================================================================

WHAT IS HAPPENING:
  When a user clicks "Continue" or "View" on a financial year in
  CompanyDashboard, handleOpenYear() is called. It:
  1. Tries to fetch data via financialDataService.getByYearId(yearId)
  2. Tries to mutate the Zustand store directly via useAppStore.getState()
  3. Navigates to /fs/cover

  There are two problems here:

  Problem 6a — Direct store mutation is wrong:
    The code does:
      useAppStore.getState().companies.forEach(c => { ... c.financialYears.forEach(y => { y.data = data.data; }) })
    This directly mutates the Zustand state object WITHOUT going through
    the immer set() function. Immer requires all mutations to go through
    the set() callback. Direct mutation bypasses reactivity — the UI
    will NOT re-render with the new data.

  Problem 6b — Wrong data shape:
    The API returns: { auditReportData, notesData, discussionData }
    The store's FinancialYear.data expects: { auditData, notesData }
    So y.data = data.data assigns the wrong shape, and auditData will
    be undefined when the /fs/cover page tries to read it.

  Result: The audit report editor opens with blank/default data instead
  of the saved data from the database.

WHERE TO FIX:
  File: frontend/src/store/useAppStore.ts
  Add a new action to properly load year data:

    loadYearData: (yearId: string, auditData: AuditReportData, notesData: N4_13_State) =>
      set(state => {
        const company = state.companies.find(c => c.financialYears.some(y => y.id === yearId));
        const year = company?.financialYears.find(y => y.id === yearId);
        if (year) {
          year.data = { auditData, notesData };
        }
      }),

  File: frontend/src/components/dashboard/CompanyDashboard.tsx
  Update handleOpenYear to use the new action:

    const handleOpenYear = async (yearId: string) => {
      try {
        const res = await financialDataService.getByYearId(yearId);
        useAppStore.getState().loadYearData(
          yearId,
          res.data.auditReportData,
          res.data.notesData
        );
      } catch (err) {
        console.error('Failed to load year data:', err);
      }
      setActiveYearId(yearId);
      navigate('/fs/cover');
    };

  isAuthChecked = true. But fetchCompanies() is called without await,
  so the sidebar may render before companies are loaded, showing
  "No companies yet" briefly before the list appears.

    setCurrentUser({ ... });
    fetchCompanies();
  To:

    await fetchCompanies();

PROBLEM 13 — LOW: Inconsistent API response shape across controllers
================================================================================

WHAT IS HAPPENING:
  Different controllers return different response shapes:

  auth, notification, stats controllers return:
    { success: true, message, statusCode, data }

  company, user, review, financialYear, financialData controllers return:
    { message, statusCode, data }  (no "success" field)

  The frontend httpClient interceptor returns response.data directly,
  so callers get different shapes. This makes error handling inconsistent
  and can cause subtle bugs when checking response.success.

WHERE TO FIX:

  Create a shared sendResponse utility in backend/src/shared/ and
  use it everywhere with: { success: true, message, statusCode, data }
